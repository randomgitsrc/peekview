## 1. 唯一 FAIL 项（决定 verdict）

### BDD-38 Then③「清单中每一项可对应到具体文件名」——不成立

这是本任务最有价值的一条证据，因为它**由证据目录自己承认**：

```
P6-evidence/logs/bdd38-41-live-http.log:19:
③ 每项可对应到具体文件名                       = False
```

同一日志给出的 `skipped[0]` 是 `{"file_id":143,"reason":"count_limit","filename":null,"path":null,"size":null}` —— 文件名确实为 `null`。

关键判定链（我逐环独立核过）：

1. **P1 文字未被批准改写**：`git log` 显示 `P1-requirements.md` 只有 `4e09219e`（P1）与 `519321ab`（P2 顺手带入）两次提交；`git diff 4e09219e 519321ab -- .../P1-requirements.md` 对 BDD-38 **零改动**。全基线共有 4 处 `[BASELINE_CHANGE]`，全部落在 `_BINARY_SIZE_LIMIT` 归属那两段，**没有一处涉及 BDD-38 的 Then③**。
2. **判据被替换而非满足**：`backend/tests/test_html_render.py::test_bdd_38_exceeding_count_limit_produces_skip_report` 的注释与断言把 ③ 写成「清单每项可按 `file_id` 定位（`filename` 可为 `null`）」，并只断言 `isinstance(item["file_id"], int)`。这是把 P1 的「可对应到具体文件名」**降级为可满足形态**。
3. **降级的来源不能反推判据**：`filename: null` 的合理性来自 P2 对 report **schema** 的设计（W5：`get_files_by_ids` 只返回命中行，溢出 id 拿不到文件名，故 schema 加 `file_id` 必填并允许 `filename` 为 null）。这是**实现层的 schema 决策**，不能用来改写 P1 的 **Then 语义**。若要改，正确程序是主 Agent 批准并在 P1 标 `[BASELINE_CHANGE: 理由]`——没有发生。
4. **架构上其实可以做到**：`count_limit` 项的 id 是客户端 `?inject=` 传来的（日志里 `skipped[0].file_id=143`），实施处 `backend/peekview/api/files.py:336-344` 直接写了 `"filename": None`。也就是说这条不是「物理不可达」，而是「选择了不查」。P2 为省一次 DB 往返放弃它——这是可辩护的权衡，但代价必须是**改判据并留痕**，而不是让 PASS 静默成立。

**裁定：BDD-38 = FAIL。** ①②④ 三项我核过都成立（`requested=41 / skipped=41`、reason ⊆ 六元闭集、`_MAX_INJECT_IDS=40 < 50-1=49`），但 BDD 是合取判据，缺一项即整条不成立。

这条**不构成方案性错误**（`rejected` 不适用）：功能骨架正确、③ 是一个可补的取数点（补一次按 id 的轻量查询即可，或按程序走 `[BASELINE_CHANGE]`）。所以是 `needs-revision`。
