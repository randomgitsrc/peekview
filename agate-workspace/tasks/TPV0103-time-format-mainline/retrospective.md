# 复盘：用 agate 全流程处理一个 3 行改动 —— 流程与任务规模严重失配

## 0. 一句话

**4702 行流程文档、3 小时、4 轮评审，换 3 行生产代码改动。** 用户在第 4 小时提出质疑，我判定流程失配、中止 agate、直接改代码，30 分钟交付。

## 1. 事实（不修饰）

| 项 | 实际数字 |
|---|---|
| 生产代码改动 | **约 3 行**（`formatFullDate` 少传两个 option）+ 拆一个常量 |
| 测试断言改动 | 5 个文件、8 处断言反转、3 处常量删除 |
| TPV0103 P1 耗时 | 10:26 → 13:21（**约 3 小时**），四轮评审（3 次打回） |
| TPV0103 产物体量 | **4702 行 markdown / 7 个文件**（P1 阶段单独） |
| 中止后实际交付耗时 | **约 30 分钟**（含 E2E 三轮调试） |
| 用户质疑时所在阶段 | P2（第 4 小时） |

## 2. 根因分析：三层，从浅到深

### 2.1 表层：agate 的 hotfix 判据不设中间档

agate 的 hotfix 判据（T074 先例）是「**≤3 行改动 + 现成测试覆盖**」。本次生产代码满足前者，但**测试要改**（26 处断言在断言 `GMT±N`）→ 判"不满足 hotfix" → 进 P0-P8 全流程。

**判据方向是对的**（测试是判据的一部分时不该自己改自己判），但它只有两个档：3 行 hotfix，或全 8 阶段。**中间的"轻量流程"是空的**。

### 2.2 中层：我把"判据严谨性"当成了目的本身

P1 四轮评审的核心争议是**如何断言才不会假绿/假红**：

| 轮次 | 判据 | 被实测推翻的原因 |
|---|---|---|
| 1 | 正则 `/GMT\|UTC\|[+-]\d/` 无命中 | 4/32 locale 假 FAIL（日期分隔符 `-` 误命中） |
| 2 | 数字段数==5 且无 GMT/UTC | `long`/`shortGeneric`/`longGeneric` 假 PASS（均 5 段） |
| 3 | 与参考输出逐字符相等 | 写法假 FAIL（Node 进程 locale ≠ 浏览器 locale） |
| 4 | +locale 轴同源 | 仍漏 timezone 轴（`TZ=UTC` 下假 FAIL） |
| 5 | 两侧都不 pin locale/timeZone | 三宿主全绿 ✅ |

**技术上都成立，但它们的产品价值是什么？** 是「P3 写测试时别踩这几个坑」。而这件事**只需要在 P3 派发单里写 5 条约束**，不需要三轮独立评审循环。

我把一个"测试实现注意事项"升级成了"需求基线的核心议题"，这是**规模误判**。

### 2.3 深层：我三次给出未经验证的结论（都在流程内被纠正）

| # | 我的错误 | 谁纠正 |
|---|---|---|
| 1 | 正则判据 `/GMT\|UTC\|[+-]\d/` 是我提的，4/32 locale 假 FAIL | analyst |
| 2 | 「任意 `timeZoneName` 恒 ≥6 段」——同一事实我上一轮实测过（表里写着 `long`=5 段），写结论时忘了 | requirements-review |
| 3 | `hour12` 方向：我测了 `hour12: true`（4/5 抓到），却拿它去"纠正" analyst 关于 `hour12: false`（4/5 逃逸）的**正确**报告 | requirements-review |

**共性**：我在 dispatch-context 里给出的"客观查证信息"混入了未核对的推断，而且**同一个事实可以实测两次仍在结论时搞错**。

**这才是流程真正的成本来源**——不是 agate 要求严，而是**我的结论不可靠，需要用三轮评审来兜底**。

## 3. 这个任务本该怎么走

用户在 P0 时问的是：「`GMT+8` 该不该出现在普通用户界面上？」

**这是一个一句话可决的产品判断**：不该（用户本地时间本无歧义，`GMT+8` 是机器格式）。定了就直接改。

正确的做法：
1. **改 3 行生产代码**
2. **改 8 处断言**（把"必须含 GMT±N"翻转为"不得含"）
3. **跑全量测试 + `TZ=UTC` 验证**（这一条是唯一的实质技术门槛，因为本机宿主恰好是 Asia/Shanghai，本地绿不可信）
4. **CHANGELOG + bump patch**
5. **写 10 行复盘记录判据演进**（供后续同类改动参考）

**总计 30 分钟**，实际也确实是 30 分钟。

## 4. agate 适用边界的修正认识

基于本次实证，我认为判据应该是：

| 条件 | 处置 |
|---|---|
| 生产代码 ≤3 行 **且** 测试不需改 **且** 无机制交叉 | **hotfix**，不走流程 |
| 生产代码少 **但测试断言需反转**（判据本身变更） | **轻量流程**：P0 一句话决策 + 直接实现 + 全量验证 + CHANGELOG，**不派 subagent、不做多轮评审** |
| 涉及 schema / 权限 / 多端契约 / 数据迁移 | **完整 agate**（TPV0102 就属这类，30 条 BDD 是合理的） |

**当前的 agate 缺中间档**。TPV0103 卡在"测试要改"上，被迫走全流程，这是机制缺口。

但对**本次**而言，**选错入口的是我**——我明知改动极小，仍按 TPV0102 的仪式规格铺开，没有在立项时评估"这件事值不值得 4 小时"。

## 6. 可复用的沉淀（唯一值得留下的东西）

**前端时间/日期格式断言的 5 条硬约束**（本次用 4 轮评审换来，后续同类任务直接套用）：

1. **不要用文本特征反推实现参数**——`timeZoneName` 有 6 种取值，其中 `long`/`shortGeneric`/`longGeneric` 的输出**既无数字偏移也不含 GMT/UTC**，且段数与正确形态**完全相同**（均 5 段）
2. **判据用「与参考格式化输出逐字符相等」**——绕开所有形态猜测
3. **参考值与被测实现必须显式同源**——Playwright 的 `test.use({locale})` **只改浏览器上下文，不改 Node 进程 locale**（后者由 env 决定）；`timezoneId` 同理
4. **`TZ=UTC` 必须单独跑一次**——本机宿主是 `Asia/Shanghai`，参考值与实现"恰好同区"会让错配永不显形，而 `ci.yml` 不跑 vitest，属"本地绿、他机红"隐性陷阱
5. **`hour12` 的错误只有 `en-US` 抓得住**——`hour12: false`（强制 24h）在 `zh-CN`/`ja-JP`/`de-DE`/`sv-SE` 输出与正确形态**完全相同**；`hour12: true` 在 `en-US` 无操作。守护点必须放在固定 `en-US` 的用例上

## 7. 关于我自己的行为

**用户在第 4 小时的质疑是对的，我应该更早产生同样的质疑。** 判断依据早在立项时就具备：改动 3 行、需求明确、无机制交叉。我没有评估"这个过程值不值"，而是默认"非平凡任务走 agate"就往下推。

**下次的判据**：立项时先问「**这个改动的实质风险是什么、需要多少验证**」，再决定流程规格，而不是按任务"类型"套模板。
