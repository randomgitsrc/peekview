## 一、任务定义

### 1.1 一句话目标

在 Peekview 现有产品内，建立一套**统一、清晰、安全**的访问认证与授权体系：让用户身份、各类访问凭证、第三方应用授权、资源权限判定之间的关系有明确定义，并让 OAuth 作为**可选能力**接入，不破坏现有部署。

## 二、为什么现在做

Peekview 已经具备四类访问能力：网站用户名密码登录（JWT + httpOnly Cookie）、用户级 API Key（`pv_` 前缀）、后端 REST API、MCP Server。这些能力**各自能工作**，但彼此之间的身份与授权关系从未被统一定义过。

具体表现（P0 实测，见第三节）：

- 三类凭证在同一个函数里按"形状"分流（几段点、什么前缀），没有类型标识
- `pv_` API Key 验证后直接返回 `User`，权限与登录完全等价，**包括 admin**
- 权限判定分散在各 service 里，API 层与 MCP 层各有一套
- 没有任何 scope / 授权范围概念，第三方应用接入只能靠"给一把全权钥匙"
- 撤销一个凭证只能删记录，无状态 Token 无法提前失效

**这与"要不要做 OAuth"无关**——即便不做 OAuth，上述关系也应当被定义清楚。OAuth 只是让这套关系第一次有了外部消费者，从而把问题暴露出来。

## 三、现状（本轮实测，全部带行号可复核）

### 3.1 三类凭证

| 凭证 | 载体 | 位置 | 权限等价性 |
|---|---|---|---|
| 会话 JWT | httpOnly Cookie `peekview_token` 或 `Authorization: Bearer eyJ...` | `auth.py:146-178` | 绑定 `User` |
| 用户 API Key | `X-API-Key: pv_...` 或 `Authorization: Bearer pv_...` | `auth.py:181-189` | **验证后返回 `User`，与登录完全等价，含 admin** |
| 全局 master key | 裸 `Authorization` 或 `X-API-Key`（非 JWT、非 `pv_`） | `api/_shared.py:90-118` | 无用户绑定，全局读 |

分流方式：`_looks_like_jwt` 只判断"3 段"（`api/_shared.py:85-87`），`pv_` 靠前缀（`auth.py:182`）。

### 3.2 已知的具体缺陷

| # | 事实 | 位置 | 影响 |
|---|---|---|---|
| A1 | `decode_access_token` 只验签名与 `exp`，**无 `aud`、无 `iss`** | `auth.py:121-135` | Token 无法约束"能用于哪个资源" |
| A2 | cookie 分支**无类型判别**，任意 token 塞进 `peekview_token` 都会走 HS256 验证 | `auth.py:158-161` | 类型混淆风险；失败时静默降级为匿名 |
| A3 | 验证失败一律 `return None`（匿名），调用方无从区分"没带凭证"与"凭证无效" | `auth.py:188` | **故障被长期掩盖**：表现为看不到内容而非授权失败 |
| A4 | `pv_` key 无 scope，等同完整用户身份 | `auth.py:181-189` | 第三方接入只能给全权 |
| A5 | `ApiKey` 模型无 scope / 无用途字段 | `models.py:267-292` | 同上 |
| A6 | 无任何 OAuth 相关表 | 生产 DB 16 张表实查 | 无 client / grant / token 存储 |
| A7 | `scope` 概念完全不存在（`grep -c scope` 在 `auth.py`/`api/_shared.py` 均为 0） | — | 无授权范围语言 |
| A8 | HS256 密钥与会话 JWT 共用 `~/.peekview/.secret_key` | `auth.py:26-28` | 会话与第三方 Token 风险绑定 |
| A9 | `/login` 在 `FRONTEND_ROUTES` 但前端**无该路由**，登录实为 `LoginDialog.vue` 弹窗 | `main.py:25` vs `router.ts` | 无独立登录页，OAuth 授权页需新建 |
| A10 | `.well-known/*` 被 SPA catch-all 吞成 `200 text/html` | `main.py:598` | **比 404 更危险**：客户端当成"端点存在"后解析失败 |
| A11 | MCP Server **只有 Streamable HTTP，无 stdio 传输** | `server.ts:2,198` | 指令要求的"本机 STDIO MCP"当前**不存在** |
| A12 | MCP 把客户端 token 原样转发给后端 API | `client.ts:39` | 对所有下游构成 passthrough 形状（见 3.4） |
| A13 | 无授权撤销管理页面 / 无"已授权应用"视图 | 前端无此路由 | 用户无法查看授予了谁什么 |

### 3.3 权限判定的现状

- 字段级：`Entry.is_public` / `owner_id` / `team_id`（`models.py`），`ApiKey` 无 scope
- 函数级：`can_read_entry(entry, user_id, is_admin, is_team_member, is_team_owner)`（`entry_service.py:89-104`）
- 依赖级：`require_auth`（401）与 `require_admin`（403）（`auth.py:191-220`）
- 匿名：`auth.allow_anonymous_create` 默认 `True`（`config.py:293-296`）

**问题**：以上全部是"你是谁 → 能看到什么"，缺少"这个凭证被授权做什么"这一维度。

### 3.4 现有 MCP 的凭证转发形状

`server.ts:104` 只检查 `pv_` 前缀，从不验证该凭证是否"签发给 MCP"；`client.ts:39` 把同一个串原样转发给后端 API。

MCP 规范（2026-07-28）对此有明文禁止：

> "If the MCP server makes requests to upstream APIs … The access token used at the upstream API is a **separate token**, issued by the upstream authorization server. The MCP server **MUST NOT** pass through the token it received from the MCP client."

`pv_` key 本来就是后端 API 的钥匙，所以这个形状长期未被察觉。**它存在与否和"做不做 OAuth"无关**，但引入 OAuth 后必须处理，否则新路径会复制同一形状。

### 3.5 版本基线

Peekview `0.28.0` / MCP Server `0.12.0`（`VERSIONS.json`）。

## 四、产品方向与约束（不可擅改）

以下来自立项指令，P1 及之后不得擅自改变。

### 4.1 产品原则

| # | 原则 |
|---|---|
| P1 | 一套产品、一套代码，不建立多产品版本 |
| P2 | **API Key 保留**，不能因引入 OAuth 而废弃 |
| P3 | **OAuth 是可选能力**，不要求所有部署开启 |
| P4 | OAuth **不依赖官方中心服务**，自部署实例独立运行 |
| P5 | 不启用 OAuth 时，现有登录、API Key、原有功能**正常工作** |
| P6 | 不要求把现有用户名密码登录改造成 OAuth 登录 |
| P7 | OAuth 授权必须关联**真实 Peekview User**，不脱离现有用户权限体系 |
| P8 | 三类凭证可关联同一用户，但**不能混为一谈**（不同类型） |
| P9 | OAuth 授权**不能扩大**用户自身已有的资源权限 |
| P10 | 用户能查看并撤销自己授予的授权 |
| P11 | 实例管理员能管理 OAuth 服务级配置 |
| P12 | **优先复用成熟实现**，不自行重复实现标准协议或密码学算法 |
| P13 | 不扩展成完整 IAM；不默认引入企业级身份管理、复杂 RBAC/ABAC、社交登录 |

### 4.2 MCP 场景原则

必须同时考虑：本机 STDIO MCP、局域网 MCP、远程 HTTP MCP、第三方 MCP Client、不同部署环境的认证与授权。

| 约束 | 说明 |
|---|---|
| 不把部署位置等同于信任度 | "本机所以安全"不是理由 |
| 不无理由要求所有 MCP 场景都用 OAuth | 需要按访问主体、资源服务器、网络边界、信任关系决定 |
| 已知差距 | **当前无 stdio 传输（A11）**，该场景需先补能力或明确排除 |

### 4.3 权限原则

**权限判定不能只看 Token Scope。** 至少需要同时考虑：

1. 用户当前实际拥有的资源权限
2. 凭证或 Grant 授予的权限范围
3. 目标资源及其访问策略
4. Token 的 Issuer / Audience / Scope 有效性约束

**失效机制必须可验证**：用户权限变化、用户被禁用、授权被撤销时，要有明确且**可验证**的失效机制。**不能只改数据库撤销标记就宣称 Token 已立即失效。**

| Token 设计（RFC 9068 + RS256/JWKS 为既定） | 未与"OAuth 可选、自部署独立"的产品约束对齐 |
| MCP 部署假设（把"公网 HTTPS 入口"当作既定目标） | 旧方案围绕公网入口设计，本任务要求覆盖本机/局域网/远程四类场景 |

### 8.3 可复用但须重新验证的研究成果

以下在旧任务中经**实测**得出，与架构选择无关，可复用但须复核是否仍成立（版本：Peekview 0.28.0 / MCP 0.12.0）：

- 第三节 A1–A13 的现状缺陷（本 brief 已重新实测，行号可查）
- MCP 规范 2026-07-28 的关键结论：DCR 已 Deprecated 且 "new implementations SHOULD NOT adopt"；CIMD 为 SHOULD；`resource` 参数为 client 侧 MUST；RS 只接受自己 token 为 MUST
- 平台侧事实：Gemini Connected Apps 需要 `registration_endpoint` **或** Play Console 手填；Claude 要求 metadata advertise `"none"` 才走 CIMD；ChatGPT 优先 CIMD
- `python-jose` 的两个坑：`access_token=True` **不校验** `typ`；`jwk.construct().to_dict()` **只产** `alg/e/kty/n`，`kid`/`use` 需手工注入
- 旧方案的两轮独立审查记录（首轮 FAIL 6 项、二轮 PASS WITH ISSUES 8 项残留）——**这是最有价值的复用物**，它记录了这类设计最容易犯的错
