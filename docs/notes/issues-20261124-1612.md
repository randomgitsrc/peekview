# Peekview：增加「全屏阅读」入口

## 1. 任务目标

在 Peekview 普通 Entry 详情页增加一个明确、易发现的「全屏阅读」入口。

用户在普通详情页选择并阅读某个文件后，可以通过一次点击，直接进入该文件对应的全屏阅读页面。

核心目标：

**让用户不需要手动修改 URL，也不需要了解 File ID，就能将当前正在阅读的文件切换到全屏模式。**

本次只补齐普通阅读模式到全屏阅读模式的操作入口，不扩展文件导航系统。

## 2. 交互设计

### 2.1 入口位置

先检查当前普通详情页的实际布局和已有操作入口。

建议优先考虑：

- 当前文件阅读区域的 Header / 工具栏。
- 如果现有详情页 Header 已有适合放置阅读操作的位置，可以复用。
- 如果当前布局没有合适位置，再考虑增加轻量的操作入口。

入口使用清晰的图标和文字，例如：

- 图标：Maximize / 全屏
- 文字：全屏阅读

具体视觉形式遵循项目现有 UI 设计规范。

要求：

1. 入口应当在用户阅读文件时容易找到。
2. 不要只放在文件树中，因为用户可能已经收起文件树。
3. 不要给文件树中的每个文件单独增加全屏按钮。
4. 不要增加独立的文件选择器。
5. 桌面端和移动端都应有合理的可发现性和可操作性。
6. 如果项目已有全屏相关图标、按钮或交互组件，优先复用。

### 2.2 点击行为

点击「全屏阅读」时，以当前实际选中的文件为目标。

分两种情况：

**情况 A：当前文件就是默认入口文件**

进入：

`/entry/f`

**情况 B：当前文件不是默认入口文件**

进入：

`/entry/f?file=<当前文件ID>`

其中：

- `entry` 替换为当前 Entry 的实际 slug。
- `file` 使用当前 Entry 中当前文件的 File ID。
- 默认入口文件必须使用统一的默认入口判断逻辑，不要简单地假定 `files[0]` 就是默认文件。

用户不需要看到或输入 File ID。

### 2.3 全屏模式

进入全屏后：

- 展示刚才选中的文件。
- 保持 `/f` 现有的 Zen / 全屏模式行为。
- 不增加文件树。
- 不增加文件选择器。
- 不额外增加复杂导航。
- 不改变原有全屏模式的纯内容阅读定位。

## 3. URL 与状态要求

本次需要与文件定位能力正确衔接。

确保：

1. `/entry/f` 打开默认入口文件。
2. `/entry/f?file=123` 打开指定文件。
3. 从普通详情页点击全屏入口，URL 自动根据当前文件生成。
4. 刷新全屏页面后，仍然展示 URL 指定的文件。
5. 无效 File ID 不得导致跨 Entry 读取，应按既定默认入口规则安全回退。
6. 不得因为页面已有的 query 清理逻辑而丢失有效的 `file` 参数。
7. 不得破坏现有 share 参数和分享权限验证。

如果指定文件的 URL 解析能力尚未实现，应先检查现有实现，并在必要时补齐最小闭环；不要假定它已经存在。

## 4. 实现前检查

请先检查当前代码和实际 UI，不要直接根据本任务描述猜测组件结构。

重点检查：

- `frontend-v3/src/views/EntryDetailView.vue`

以上是检查线索，不要求所有文件都修改。

需要确认：

1. 当前全屏入口是否已经存在于其他位置，是否可以复用。
2. 当前文件选择状态由哪个组件或 Store 管理。
3. 全屏模式目前如何切换。
4. 当前文件 ID 如何取得。
5. 默认入口文件如何判断。
6. 是否已有 `file` query 参数的解析能力。

如果发现相关能力已经实现，不要重复实现。

## 5. 验收标准

### 桌面端

- 普通详情页能够清楚看到「全屏阅读」入口。
- 当前选中默认文件时，点击后进入 `/entry/f`。
- 当前选中非默认文件时，点击后进入 `/entry/f?file=<id>`。
- 不需要展开文件树也能使用该入口。
- 进入全屏后正确展示当前文件。

### 移动端

- 有明确、可触达的全屏入口。
- 不遮挡主要内容。
- 点击后正确进入对应文件的全屏模式。

### 兼容性

- 单文件 Entry 正常。
- 多文件 Entry 正常。
- README、index 等默认入口规则正常。
- Share 页面和权限验证不受影响。
- 原有手动在 URL 后追加 `/f` 的方式继续有效。
- 全屏模式原有布局和行为不被破坏。

## 6. 本次不做

- 不新增全屏文件树。
- 不新增全屏文件选择器。
- 不给文件树中的每个文件增加全屏按钮。
- 不新增 `main_file` 数据字段。
- 不新增文件身份协议。
- 不改变 `/f` 的 URL 语义。
- 不改变全屏模式的视觉定位。
- 不扩展为 Agent 项目管理或文件管理功能。

## 7. 交付要求

完成后请说明：

1. 全屏入口最终放在什么位置，为什么选择这个位置。
2. 修改了哪些文件。
3. 如何保证进入全屏时使用的是当前选中的文件。
4. URL 如何生成和解析。
5. 桌面端、移动端及单文件、多文件场景的测试结果。
6. 是否存在尚未解决的问题。

优先采用最小改动，复用现有组件和状态管理。

**最终原则：普通页面负责选择和阅读文件，全屏入口负责将当前文件带入纯阅读模式。用户只需点击一次，不需要理解 URL 参数。**
