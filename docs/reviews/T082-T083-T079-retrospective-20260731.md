## 2. 问题识别与分析

### 2.1 技术原因

#### P-TECH-1: opencode subagent 类型不存在导致首次派发失败

**现象**：T083 P1 analyst 和 P2 architect 首次派发用 `subagent_type: "backend"`，返回 `Model not found: inherit/.`；T079 P1 analyst 用 `subagent_type: "frontend"` 同样失败。需要回退到 `subagent_type: "general"` 重试。

**根因**：opencode 的 `backend`/`frontend` subagent 类型配置缺失或模型未正确映射。`general` 类型可用但 `backend`/`frontend`/`security` 不可用。

**定位**：
- 非 agate 协议问题——agate 不指定 subagent 类型
- 非 LLM 问题——模型未加载
- opencode 平台配置问题——`~/.config/opencode/agents/` 目录下缺少对应 agent 定义或模型映射

**影响**：每个任务浪费 2-4 个 subagent session 调用（~30 秒），但不阻塞流程（主 Agent 自动回退到 general）。

**证据**：
- T083: `T083 P1 analyst (@backend subagent)` 0 tokens, 0 output
- T083: `T083 P2 architect (@backend subagent)` 0 tokens, 0 output
- T083: `T083 P4 review (@security subagent)` 0 tokens, 0 output
- T079: `T079 P1 analyst (@frontend subagent)` 0 tokens, 0 output

#### P-TECH-2: check-tdd-red.sh 不兼容 vitest 输出格式

**现象**：T083（pytest）check-tdd-red.sh 正常工作；T079（vitest）check-tdd-red.sh 反复返回 `unexpected test result — exit=1, failed=0, errors=0`，导致 P3 gate 多次不通过。

**根因**：check-tdd-red.sh 的 `RUNNER_FLAGS` 默认 `-q`（为 pytest 设计），追加到 vitest 命令后导致 vitest 崩溃（`-q` 不是 vitest 的有效参数）。同时 vitest 的输出格式 `Test Files  2 failed (2)` 与 pytest 的 `2 failed` 格式差异导致正则匹配不稳定。

**定位**：
- agate 协议问题——check-tdd-red.sh 是 pytest 参考实现，非语言无关
- 非 LLM 问题
- 非 opencode 问题

**影响**：T079 P3 gate 阻塞约 30 分钟（多次 commit 尝试 + 调试 gate_commands.P3 值 + 最终用 p3-runner.sh 包装脚本绕过）。

**证据**：
- T079 P2-design.md gate_commands.P3 被改了 3 次：`cd frontend-v3 && npx vitest run --reporter=verbose` → `npx vitest run --reporter=verbose` → `backend/.venv/bin/python -m pytest backend/tests/ -v --tb=short` → 最终用 `p3-runner.sh` 包装
- 3 次 commit 被 pre-commit gate 拦截

#### P-TECH-3: P3 测试代码质量低导致 P4 阶段额外修复

**现象**：T079 P3 test-designer 产出的测试代码有 4 类 bug，导致 P4 阶段需要额外修复测试代码而非只写实现代码：

1. `vi.mock` hoisting 问题（UserMenu.spec.ts 16/16 失败）——在函数内部调用 `vi.mock`，vitest hoisting 后闭包变量不存在
2. `:has-text()` 选择器（T079-entry-detail-header.spec.ts 2/22 失败）——Playwright 语法用于 Vue Test Utils
3. `vi.doMock` 缓存不更新（admin badge 1/22 失败）——`vi.doMock` 不影响已导入模块
4. `find('button')` 选择器不精确（BDD-05）——找到 copy button 而非 AuthButton

**根因**：LLM 生成的测试代码对 vitest mock 机制理解不正确。`vi.mock` 是 hoisted 的（编译时提升到文件顶部），不能在函数内部使用闭包变量。这是 vitest 的特有行为，与 jest 的 `jest.mock` 行为一致但 LLM 未能正确迁移知识。

**定位**：
- LLM 问题——test-designer subagent 对 vitest mock hoisting 机制理解不正确
- 非 agate 协议问题——协议不限制测试框架选择
- 部分是 agate 问题——P3 check-tdd-red.sh 的 A/B 类区分在 P3 阶段是有效的：`vi.mock` hoisting 问题在 P3 时表现为 collection error（import 失败），被正确判定为 B 类红灯放行（因为实现尚未编写，import 失败是合理的）。问题出在 P3→P4 过渡期：P4 实现完成后，测试代码自身的 mock bug 从 import 失败转变为 assertion failure，但此时 check-tdd-red.sh 已不参与（P4 gate 走全量测试）。check-tdd-red.sh 的 A/B 类区分在其职责范围内（P3）是正确的，无法在 P3 阶段捕获此类「P3 时表现为 B 类、P4 时暴露为 A 类」的潜伏 bug

**影响**：P4 阶段额外消耗 ~30 分钟修复测试代码（UserMenu.spec.ts 重写 mock 模式 + T079-entry-detail-header.spec.ts 修选择器 + t067-detail-framework.spec.ts 适配 11 项）。

**证据**：
- T079 P4-implementation.md 声明 6 条 DESIGN_GAP，其中 4 条是 P3 测试代码问题
- T079 P4 阶段一个独立的 subagent session（`Fix T067 tests for T079`）专门修复 t067 测试
- UserMenu.spec.ts 从 `vi.mock` 函数内调用改为模块级可变 mock 对象

#### P-TECH-4: P7 DESIGN_GAP 转抄格式不匹配 gate 正则

**现象**：T079 P7-consistency.md 产出了 6 条 DESIGN_GAP_REVIEWED，但 gate 报 `P7 只转抄了 0 条`。

**根因**：P7 subagent 用 `> [DESIGN_GAP:` 格式（markdown 引用块）转抄 P4 的 DESIGN_GAP，但 check-gate.sh 的正则 `^\s*-?\s*\[DESIGN_GAP:` 要求行首（允许空格和可选 `-` 前缀），不匹配 `> ` 前缀。

**定位**：
- agate 协议问题——gate 正则与角色文件中的转抄示例格式不匹配。角色文件未明确要求行首格式，subagent 自然使用了 markdown 引用块
- 非 LLM 问题——subagent 的转抄内容是正确的，只是格式不匹配

**影响**：P7 gate 1 次不通过，主 Agent 手动 `sed` 修复格式后通过（~5 分钟）。

**证据**：
- `sed -i 's/^> \[DESIGN_GAP:/[DESIGN_GAP:/g'` 修复后 gate exit 0

#### P-TECH-5: make publish token 读取在非交互 shell 中失败

**现象**：`make publish` 在 opencode 环境中报 `PYPI_API_TOKEN not set`，需要手动 `export PYPI_API_TOKEN=...` 才能发布。

**根因**：Makefile 的 token 读取逻辑用 `bash -c 'source "$1" ...'` 从 `~/.env` 加载 token。在交互 shell 中 `~/.bashrc` 用 `set -a && source ~/.env && set +a` 加载并自动 export；但在 opencode 的非交互 shell 中，`~/.bashrc` 不会自动执行，`source ~/.env` 只赋值不 export，导致子进程（twine）拿不到 token。

**定位**：
- 项目基础设施问题——Makefile 依赖 shell 环境的 `set -a` 行为
- 非 agate 问题
- 已修复：Makefile 加 `set -a` 确保 source 后变量自动 export（commit `43c694fb`，在 v0.13.0 tag 之后、推送到远端之前修复）

**影响**：发布延迟 ~10 分钟（3 次 `make publish` 尝试 + 排查 token 加载链）。

**证据**：
- `e63db696 fix(makefile): publish 兜底读取 ~/.env`（之前修复过类似问题但未加 `set -a`）
- `43c694fb fix: make publish token 读取加 set -a 确保变量 export 到子进程`

### 2.2 管理原因

#### P-MGMT-1: 主 Agent 在 P4 阶段修复 P3 测试代码 bug

**现象**：T079 P4 阶段，主 Agent 直接修复了 P3 test-designer 产出的测试代码 bug（UserMenu.spec.ts mock 模式重写 + T079-entry-detail-header.spec.ts 选择器修复），而非退回 P3 重派 test-designer。

**根因**：agate v0.25.0 P4 卡片规定「P4 不修测试代码，只写实现」。但 P3 产出的测试代码有 bug（A 类错误），P4 implementer 无法通过这些测试。正确流程是退回 P3 修复测试代码，但主 Agent 选择了直接修复以节省时间。需要注意的是：即使退回 P3，check-tdd-red.sh 仍会判为 B 类红灯放行（因为 import 失败），test-designer 未必能发现 mock hoisting bug——退回 P3 并不能保证修复，根本问题是 P3 的 gate 无法捕获此类「P3 时表现为 B 类、P4 时暴露为 A 类」的潜伏 bug。

**定位**：
- agate 执行合规问题——主 Agent 绕过了 P3→P4 退回流程
- 管理决策——在「严格合规」和「效率」之间选择了效率
- 根因是 P-TECH-3（LLM 测试代码质量）的下游影响

**影响**：P4 产出中 6 条 DESIGN_GAP 有 4 条是 P3 测试代码问题，P7 一致性检查需要全部 REVIEWED。未阻断流程但增加了 P4/P7 的复杂度。

**证据**：
- T079 P4-implementation.md 中 DESIGN_GAP #2~#5 全部标注「P3 测试基础设施问题，非组件实现问题」
- 主 Agent 直接编辑了 UserMenu.spec.ts 和 T079-entry-detail-header.spec.ts

#### P-MGMT-2: 主 Agent 在 P6 阶段编辑 P1-requirements.md 处理 NEED_CONFIRM

**现象**：T079 P1-requirements.md 有 1 条 `[NEED_CONFIRM]`（Settings 导航 URL），主 Agent 在用户睡觉期间直接做了默认裁定（选项①：文案改为 "Settings" + URL 保持 `/settings?tab=apikeys`），改为 `[SCOPE_RESOLVED]`。

**根因**：agate 协议要求 `[NEED_CONFIRM]` → PAUSED 等人确认。但用户明确说「我睡觉了」，主 Agent 需要在无人值守下完成。做了合理的默认决策——该决策不涉及业务方向（DESIGN.md 只规范文案，不限制 URL），只是 UX 细节。

**定位**：
- agate 执行合规问题——绕过了 PAUSED 流程
- 管理决策——在「严格暂停」和「自主推进」之间选择了自主推进
- 风险可控——决策不涉及业务方向，只涉及实现细节

**影响**：无实际负面影响。决策合理，P2/P4/P6/P7 全链路一致验证。

#### P-MGMT-3: check-tdd-red.sh 对非 pytest 项目的适配依赖 workaround

**现象**：T079 P3 gate_commands.P3 被修改 3 次，最终用 `p3-runner.sh` 包装脚本绕过 check-tdd-red.sh 的 `-q` flag 追加行为。

**根因**：agate v0.25.0 check-tdd-red.sh 的 `RUNNER_FLAGS` 默认 `-q`，设计为 pytest 的 `--quiet` 参数。vitest 不认识 `-q`，导致崩溃。P2-design.md 的 gate_commands.P3 声明了 vitest 命令，但 check-tdd-red.sh 追加 `-q` 后命令不合法。

**定位**：
- agate 协议问题——check-tdd-red.sh 是 pytest 参考实现，未充分适配非 pytest 项目
- gate_commands.P3 声明的是完整命令，check-tdd-red.sh 不应追加额外 flag
- v0.25.0 已有 `TEST_RUNNER_FLAGS` 环境变量覆盖机制，但 commit hook 中不会设置

**影响**：T079 P3 gate 阻塞 ~30 分钟。T083（pytest）不受影响。

## 5. 待讨论问题

1. **check-tdd-red.sh 是否应该对 vitest 做一等公民支持？** 当前 vitest 项目需要用 p3-runner.sh 包装脚本绕过。如果 agate 要支持多语言项目，check-tdd-red.sh 需要语言无关或至少支持 vitest/jest/go test 等。

2. **P3 A 类红灯（测试代码 bug）应该阻断还是放行？** 当前 check-tdd-red.sh 对 collection error（import 失败）判为 B 类（exit 0 放行）。但如果 import 失败是因为测试代码自身有 bug（如 `vi.mock` hoisting 导致 `ReferenceError`），这不是「实现未写」而是「测试代码有 bug」。如何区分？

3. **无人值守模式下的 NEED_CONFIRM 处理策略？** 用户说「我睡觉了」时，主 Agent 需要自主推进。是否有比 PAUSED 更好的机制？建议增加 `auto_resolve_policy` 字段。

4. **P7 DESIGN_GAP 转抄格式是否应该在角色文件中明确？** 当前 architect.md 只说「转抄 + REVIEWED」，不指定格式。gate 正则要求行首格式。subagent 自然使用了 markdown 引用块。是否应该在角色文件中给出格式示例？
